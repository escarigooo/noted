# Demo and deployment

## Supported local demo

Docker Compose is the supported, reproducible workflow. It starts the Flask app behind Gunicorn, MySQL 8.4 with deterministic synthetic fixtures, and Mailpit for captured email.

```bash
docker compose up --build
```

- App: http://localhost:8080 (override with `NOTED_PORT`)
- Health: http://localhost:8080/health
- Mailpit: http://localhost:8025
- Demo admin: `admin@example.com` / `DemoOnly!2026`
- Demo customer: `demo01@example.com` / `DemoOnly!2026`

These credentials are public demo-only fixtures. Never reuse them elsewhere.

To stop the demo, run `docker compose down`. To reset all database and generated invoice state, run `docker compose down --volumes`, then start it again. Deleting named demo volumes is intentional and destructive only to local synthetic demo state.

The Windows `.bat` files are convenience wrappers, not a second deployment system. `start_project.bat` delegates to Compose; `setup_venv.bat` creates a local Python environment for contributors.

## Local checks

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/ruff check .
.venv/bin/python -m pytest
.venv/bin/pip-audit -r requirements.txt
docker compose config --quiet
docker build .
```

Notebook dependencies are isolated in `requirements-analytics.txt`. Notebooks are offline experiments and are never executed by an HTTP request.

## Hosted demo contract

Deploy the `Dockerfile` to a container platform with a private, persistent MySQL service. Configure `SECRET_KEY`, `DATABASE_URI`, SMTP settings, `SITE_URL`, and `INVOICE_DIR` through the platform secret/environment manager. Use an ephemeral invoice directory for a disposable demo or an explicitly managed private volume if files must survive restarts.

The container runs as a non-root user and starts Gunicorn through `wsgi.py`. The platform should use `/health` as its readiness probe. Do not expose MySQL or Mailpit publicly.

No automatic production deployment is enabled. The owner has chosen to defer hosting until a personal VPS is available. CI validates tests, dependency vulnerabilities, complete reachable secret history, and the container build on pull requests and pushes to `main`.

## Hosting assessment (2026-09-01)

A hosted demo is optional for this portfolio project. The verified local Compose demo and factual case study remain valid without a permanent public environment.

If a separate hosted demo is wanted before the VPS exists, **Railway Hobby is the assessed fallback**:

- Railway automatically builds a root `Dockerfile` and provides private networking between services.
- Its MySQL template is quick to provision and private by default, but Railway explicitly classifies database templates as **unmanaged**. Backups, maintenance, security, and recovery remain the owner's responsibility.
- Hobby currently costs USD 5/month and includes USD 5/month of resource usage. Usage above that allowance is billed separately, so a usage limit must be configured.

The alternatives add more work for this particular application:

- Render can run the web container and a private MySQL container with a persistent disk, but MySQL is not one of Render's managed datastores. Free web services cannot attach persistent disks, so a durable MySQL demo is not fully free.
- Fly.io documents MySQL as a self-managed application with a persistent volume and recommends 2 GB RAM for MySQL 8. This gives more infrastructure control than a disposable CV demo needs.

Official references: [Railway plans](https://docs.railway.com/pricing/plans), [Railway Dockerfiles](https://docs.railway.com/builds/dockerfiles), [Railway MySQL](https://docs.railway.com/databases/mysql), [Render free services](https://render.com/docs/free), [Render MySQL](https://render.com/docs/deploy-mysql), and [Fly.io MySQL](https://fly.io/docs/app-guides/mysql-on-fly/).

Do not create provider resources until the repository owner has approved the provider and recurring-spend ceiling. For the planned VPS, keep the web application and MySQL on a private container network, expose only the reverse proxy over HTTPS, store secrets outside Compose, configure backups and a firewall, and verify `/health` after deployment.

## Limitations

- Checkout is simulated; no real card fields or payment provider exist.
- Email requires configured SMTP; Mailpit only captures local messages.
- PDFs are simple demo invoices generated by ReportLab.
- Analytics is calculated from the application database; notebooks are not a production pipeline.
- The demo reset discards all mutable state by design.
